# VC2M8A04 — Mathematics

## Snapshot
- **Descriptor:** VC2M8A04. Use algorithms and related testing procedures to identify and correct errors.
- **Year level / Learning area:** Years 7–8, Mathematics (Algebra).
- **Big ideas:**
  - An algorithm must be tested systematically to confirm it works correctly.
  - Errors can be in logic (wrong steps), in computation (wrong numbers) or in sequencing (right steps, wrong order).
  - Testing with known answers and edge cases reveals hidden errors.
- **Curriculum hooks:** Numeracy; Critical and Creative Thinking; Technologies (Digital).

## What you are learning
- You are learning to **use algorithms and related testing procedures** to **identify and correct errors**.
- You are learning to think about testing as a normal part of mathematical problem-solving, not an afterthought.

By the end of this you should be able to:
- Trace through an algorithm step by step with given inputs (a "dry run").
- Identify where an error occurs by comparing expected and actual outputs.
- Classify the error as logic, computation or sequencing.
- Correct the error and re-test to confirm the fix.

## Core content

**1. What is an error in an algorithm?** An **error** (or "bug") is any point where the algorithm produces an incorrect or unexpected output. Errors can be: **logic errors** (the rule itself is wrong), **computation errors** (arithmetic mistake within a correct rule) or **sequencing errors** (steps in the wrong order). *Quick check:* What is the difference between a logic error and a computation error?

**2. Tracing (dry run).** A **trace** means following the algorithm step by step with a specific input, recording the value of each variable after each step. This is the most reliable way to find where things go wrong. Use a trace table: one column per variable, one row per step. *Quick check:* Why is tracing more reliable than just reading the algorithm?

**3. Testing with known answers.** Choose inputs where you already know the correct output. Run the algorithm. If the output matches, that test passes. If not, the trace shows which step produced the error. Example: to test a formula for the area of a rectangle, use *l = 5*, *w = 3* and confirm the output is 15. *Quick check:* Why should you test with more than one set of inputs?

**4. Edge cases.** An **edge case** is an unusual or extreme input — zero, one, the largest possible value, a negative number. Algorithms often fail at boundaries. Example: a division algorithm should be tested with a divisor of 1 and checked for behaviour when the divisor is 0. *Quick check:* Name an edge case for an algorithm that calculates the average of a list of numbers.

**5. Identifying the error location.** Compare the trace output at each step with what you expect. The first step where actual ≠ expected is the error location. Then ask: is the rule wrong (logic), is the arithmetic wrong (computation), or are the steps in the wrong order (sequencing)? *Quick check:* An algorithm gives the correct answer for *x = 2* but the wrong answer for *x = 0*. What type of error might this be?

**6. Worked example — correcting a perimeter algorithm.** A student writes an algorithm to find the perimeter of a rectangle: Step 1: Read *l* and *w*. Step 2: Calculate *P = l + w*. Step 3: Output *P*. Test with *l = 5*, *w = 3*: algorithm outputs 8, but the correct perimeter is 16. Trace: Step 2 is wrong — the rule should be *P = 2(l + w)* or *P = 2l + 2w*. This is a **logic error**. Fix: change Step 2. Re-test: *P = 2(5 + 3) = 16*. Correct. *Follow the thinking:* run the test → compare output with expected → trace to find the faulty step → classify the error → fix → re-test.

**7. Iterative correction.** Sometimes fixing one error reveals another. After each correction, re-test with all your original test cases plus any new ones the bug suggested. This cycle — test, find, fix, re-test — is how professional programmers and mathematicians ensure reliability. *Quick check:* Why should you re-run all tests after fixing one error, not just the failing test?

## Try these scenarios

1. **Everyday.** You write an algorithm to convert Celsius to Fahrenheit: Step 1: Multiply by 1.8. Step 2: Add 32. Test with 0°C (expected: 32°F) and 100°C (expected: 212°F). Both work. Test with −40°C. Does it give −40°F? If not, where is the error?
2. **Civic.** A Brimbank City Council algorithm calculates bin-collection fees: *Fee = $80 + $15 per extra bin*. A resident with 2 extra bins is charged $125. Trace the algorithm and identify the error.
3. **Vocational.** A bakery apprentice's recipe algorithm says "double all ingredients for a large batch." The small batch uses 250 g flour and 2 eggs. The doubled batch has 500 g flour but 3 eggs. Identify and classify the error.
4. **Ethical.** A banking algorithm calculates interest incorrectly for accounts with a zero balance, charging fees on non-existent money. Discuss why edge-case testing is an ethical responsibility.
5. **Cross-cultural.** A school maths-trail algorithm guides students through five stations. A group arrives at station 3 before station 2 because the direction step is wrong. Classify the error and suggest a fix.

## Memorable takeaways
- Trace through algorithms step by step with test inputs.
- Compare actual output with expected output at every step.
- Classify errors: logic, computation or sequencing.
- Test with normal inputs, known answers and edge cases.
- Fix, then re-test everything — one fix can reveal new errors.

## Watch out for these traps
- "If it works for one input, it works for all." One passing test does not prove correctness — always test multiple inputs including edge cases.
- "The last step is always where the error is." The error might be in an earlier step; it just becomes visible in the output.
- "Fixing one error fixes everything." A fix can introduce new errors or reveal previously hidden ones. Always re-test.
- "Edge cases don't matter." They are where most real-world errors occur (zero values, maximum values, empty inputs).

## Model responses

Use these to check your own thinking after you have had a go.

**Quick checks (Core content)**

1. *Logic vs computation error.* Logic: the rule itself is wrong (e.g., using + instead of ×). Computation: the rule is correct but the arithmetic is wrong (e.g., 3 × 5 = 12 instead of 15).
2. *Why trace is more reliable.* It forces you to check every intermediate value, not just the final output — errors become visible where they occur.
3. *Test with more than one input.* A single test might pass by coincidence. Multiple inputs test different paths and catch errors that only appear for certain values.
4. *Edge case for averaging.* An empty list (zero numbers) — the algorithm would divide by zero.
5. *Correct for x = 2, wrong for x = 0.* Likely a logic error involving division by zero or a step that assumes x ≠ 0.
6. *Re-run all tests.* A fix might accidentally break something that previously worked. Full re-testing catches this.

**Try these scenarios**

1. *Celsius to Fahrenheit.* −40 × 1.8 + 32 = −72 + 32 = −40°F. It works correctly (−40 is the point where both scales meet). If it failed, the error would be in Step 1 (multiplication).
2. *Bin fees.* Expected: $80 + $15 × 2 = $110. Charged: $125. Trace: likely computed $15 × 3 (counted the standard bin as an extra) — logic error in defining "extra."
3. *Bakery.* Flour doubled correctly (250 → 500). Eggs wrong (2 → 3, should be 4). Computation error: 2 × 2 was calculated as 3.
4. *Banking edge case.* Charging fees on zero balance harms customers and may violate consumer law. Edge-case testing is an ethical duty because errors at boundaries cause real financial harm.
5. *Maths trail.* Sequencing error — the direction to station 2 sends students to station 3 first. Fix: swap the direction steps for stations 2 and 3, then re-test the full route.

**Stretch task — example shape of a strong answer.** Algorithm: Step 1: *bus = 300 ÷ n*. Step 2: *total = bus + entry*. Logic error planted: Step 2 uses × instead of +. Computation error: bus hire is $300 but written as $30. Test 1: *n = 30*, entry = $10. Expected: 300/30 + 10 = $20. Faulty output: (30/30) × 10 = $10. Trace reveals Step 1 uses wrong value ($30) and Step 2 uses × instead of +. Fix both. Re-test: 300/30 + 10 = $20. Correct. Edge case: *n = 1* → 300 + 10 = $310. Works.
